# 04 · 设备插件包（MPK / RN bundle）下载与结构

写于 2026-11-20。**接口已打通并真机验证**，这是本项目的第 4 条逆向主线（前三条：云端协议、规格层、局域网）。

## 1. 为什么这条重要

米家里每台设备的**具体 UI 与业务规则**（控件布局、温度×时长这类限制、文案）有三种来源：

| 来源 | 适用设备 | 我们能不能读 |
|---|---|---|
| MIoT spec | 所有设备 | ✅ 已完整接入（`01-网络与签名.md` 第 5 节） |
| **插件包（本条）** | 有插件的老/复杂设备 | ✅ **本文档** |
| 设备固件 / 面板 | 无插件的简单设备 | ❌ 只能实测（见 `03-真机行为记录.md`） |

空气炸锅 `careli.fryer.maf04` 就是第三种 —— 它**没有插件**，所以那股「温度→时长」的曲线在 App 里根本不存在，纯粹是固件逻辑。这解释了为什么在 APK 里怎么搜都搜不到。

## 2. 接口

```
POST /v2/plugin/fetch_plugin
Content-Type: application/x-www-form-urlencoded   （data=<上面的 JSON>，走标准签名）
```

### 2.1 必须用嵌套结构（关键坑）

APK 里的调用方是 `DeviceRenderer.java:256-310`。**扁平请求体（`{"model": ...}`）会让服务端返回全 null**，
必须按它构造 `latest_req` / `backup_req` 两份：

```json
{
  "is_car_mihome": false,
  "latest_req": {
    "app_type": 10119,
    "app_platform": "android",
    "region": "cn",
    "plugins": [{"model": "minij.washer.v5"}],
    "package_type": ""
  },
  "backup_req": {
    "plugins": [{"model": "minij.washer.v5"}],
    "api_level": 111,
    "app_platform": "android"
  }
}
```

字段来源：`app_type=10119`（`DeviceRenderer.java:266`）、`api_level=111`（`:290`）、
`app_platform`（`:267`，取值为 `android` / `phone` 都行）、`region`（`:272`，取自全局 server 配置）。

### 2.2 返回

```json
{"backup_info": [{
  "model": "minij.washer.v5",
  "plugin_id": 1155,
  "version": 493,
  "package_name": "com.minij.jump.normalv5",
  "type": "MPK",
  "length": 3760428,
  "download_url": "http://iot-cdn0.io.mi.com/default/com.minij.jump.normalv5_2019….zip?GalaxyAccessKeyId=…&Signature=…",
  "safe_url": "",
  "change_log": "", "force": 0, "api_level": 0
}]}
```

`plugin_id == 0` ⇒ **该型号没有插件**（不是出错）。`download_url` 是带签名的 CDN 直链，`length` 与实际下载字节一致（校验过）。

### 2.3 实测结果（真实账号，2026-11-20）

| 型号 | plugin_id | 版本 | 包名 | 大小 |
|---|---|---|---|---|
| `minij.washer.v5`（洗衣机） | 1155 | 493 | `com.minij.jump.normalv5` | 3,760,428 B |
| `xiaomi.tv.fsv1`（电视） | 102 | 57 | `com.xiaomi.plug.mitv` | 1,507,199 B |
| `careli.fryer.maf04`（空气炸锅） | **0** | — | — | 无插件 |
| `yeelink.light.mbulb3`（灯泡） | **0** | — | — | 无插件 |

## 3. 包结构

`type: "MPK"`，本质是 Android APK 风格的 zip：

```
AndroidManifest.xml
classes.dex              ← 原生代码
resources.arsc
res/                     ← 原生资源（含 i18n 文案）
assets/
  index.android.bundle   ← React Native 的 JS 包（明文！）
  fonts/…  LicenseService.html  PrivacyPolicy.html
META-INF/                ← 签名（CERT.RSA / CERT.SF / MANIFEST.MF）
```

洗衣机包共 **593 个条目**，`assets/index.android.bundle` = **2,138,153 B**，开头是
`(function(global…` —— **明文 JavaScript，不是 Hermes 字节码**，可以直接读。

⚠️ 但该 bundle 里**一个中文都没有**（`温度/时长/分钟/上限` 全部 0 命中，`\uXXXX` 转义也试过）。
说明这代插件的 **i18n 在原生 `res/` / `resources.arsc` 里**，JS 只放逻辑。
要读文案得解 `resources.arsc`；要读业务规则则要读 dex —— 两条都比读 JS 重。

## 4. 客户端实现

`mihome_pc/xiaomi/plugin.py`（纯标准库、Python 3.8）：

```python
from mihome_pc.xiaomi import plugin

info = plugin.fetch_plugin_info(client, "minij.washer.v5")   # None = 无插件
path = plugin.download_package(info, "out/plugins")           # 下载 zip
names = plugin.extract(path, "out/plugins/extract")           # 解包
js    = plugin.bundle_text(path)                              # 取 RN bundle 文本
hits  = plugin.search_rules(js, (u"上限", u"时长"))            # 关键词上下文
```

## 5. 还没做的

1. **解 `classes.dex` 读业务规则**（需要 dex 反汇编，本机有 jadx 可用于 dex）。
2. **解 `resources.arsc` 读文案**（Android 资源表，格式公开但解析量大）。
3. 用插件里的规则替换 `assets/dynamic_ranges.json` 中靠实测得来的条目 ——
   目前空气炸锅那条**只能保留实测值**，因为它没有插件。

## 6. 复现命令

```bash
# 环境：已登录过（data/credentials.json 存在）
python -c "from mihome_pc import cli; from mihome_pc.xiaomi import plugin; \

```

## 7. 第二轮补充（2026-11-20）：两个包形态不同

| 型号 | 条目数 | 有 RN bundle？ | 中文文案在哪 |
|---|---|---|---|
| minij.washer.v5 | 593 | ✅ assets/index.android.bundle（2,138,153 B，明文 JS，无中文） | `resources.arsc`（实测 ` 温度 ` / ` 分钟 ` 命中） |
| xiaomi.tv.fsv1 | 347 | ❌ 没有任何 `bundle` / `.js` 条目，**纯原生** | `resources.arsc` |

结论：
* 插件有**两种形态** —— 混合（原生 + RN）与纯原生，不能用「一定有 main.bundle」的假设去处理；
  `plugin.bundle_text()` 对纯原生包返回 `None`，这是正常结果不是错误。
* 文案统一在 **`resources.arsc`**（Android 资源表）。要读文案就解析 arsc，要读业务规则就反 `classes.dex`
  —— 两条都比「读明文 JS」重，本机有 jadx 可处理 dex。

## 8. 目标结论：空气炸锅那条不适用，有证据

`careli.fryer.maf04` 在 `/v2/plugin/fetch_plugin` 下返回 `plugin_id = 0`，
即**官方没有为它下发任何插件**（同批测试里 `yeelink.light.mbulb3` 亦然）。
因此「用插件里的官方规则校验温度×时长曲线」在这台设备上**结构性地不可能**；
该曲线只能在固件/面板侧存在，已用用户实测值编码进 `mihome_pc/assets/dynamic_ranges.json`。

反过来这也确认了我们通用 spec UI 的正确性：**没有插件的设备，走的就是 spec 渲染**，和她看到的米家表现一致。

## 9. 第三轮（2026-11-20 下午）：把插件拆到「文案」和「代码」两层

### 9.1 文案层：已完全拿下

写了 tools/plugin_strings.py（纯标准库解析 `resources.arsc` 的字符串池）：

| 插件 | 资源字符串 | 含中文 |
|---|---|---|
| minij.washer.v5 | 3,132 | **542** |
| xiaomi.tv.fsv1 | 1,538 | 77 |

导出的目录：out/plugins/strings/<model>.json。里面有大量可直接复用的官方文案，例如
` 主洗时间 `、` 洗涤温度 `、` 剩余时间 `、` %1%2%3 `，以及完整的故障排查话术
（` 检查温度传感器（NTC）的插线是否有接触不良 ` 等）。

**还捞到一条真正的业务规则字符串**：

```
筒自洁模式下不能预约，请重新选择模式
筒自潔模式下不能預約，請重新選擇模式
```

这证明：**插件的业务规则是硬编码在代码里的，不是数据表** —— 与我们此前对空气炸锅"曲线只在固件"的判断一致。

### 9.2 代码层：反编译成功，规则待定位

用 reverse/tools/jadx.ps1 反编译插件 APK（先复制成 .apk）：

```
jadx --no-res --no-imports -d out/plugins/jadx-washer out/plugins/minij.washer.apk
→ 584 个 java 文件，成功
```

**卡住的地方**：Java 里没有中文字面量（` 筒自洁 ` 搜不到），代码只用 R.string.xxx 的数字 id 引用文案。
所以要把「文案 → 资源 id → 代码位置」连起来，需要一个完整的 `resources.arsc` 资源名映射。

tools/arsc_map.py 已能解析包结构（实测：包名 com.minij.jump.normalv5、
12 个类型 anim/array/.../string/style、string 类型有 96 个 config 分片），
但**目前只映射出 896 条且多为文件引用**（如 res/anim/appear.xml），
` string ` 类型下的中文条目没被正确取出 —— 大概率是带样式的 complex entry 被跳过，
或 entry 偏移解析有偏差。下一步要用真实 dump 对齐格式（aapt2 dump resources 可作对照）。

### 9.3 结论与建议

* **要文案**：已经够了，plugin_strings.py 直接用。
* **要规则**：还需要打通「资源名映射」，然后再在 584 个 java 文件里定位判断逻辑；
  这是**数小时级**的活，不是一轮能收的。
* 优先级别建议：**先出可运行版本**（打包），插件规则挖掘作为后续独立课题。

## 10. 第四轮（2026-11-21）：文案表打通了，「规则在代码里」这个前提被证伪

### 10.1 卡点不在偏移解析，在**多语言分片谁赢**

§9.2 的猜测（complex entry 被跳过 / entry 偏移有偏差）都不对。真正的原因很朴素：

* `string` 类型有 **94 个 config 分片**（`default`、`af`…`zu`，含 `zh`/`zh-rCN`/`zh-rHK`/`zh-rTW`）；
* 原型 `resource_map()` 按文件顺序遍历，**后者覆盖前者**，最后一个中文分片是 `zh-rTW`；
* 于是 339 条中文全在，只是全变成了**繁体**。用简体关键词去 grep（`筒自洁`）自然一条都不中，
  又被解读成「string 类型下的中文没取到」。

修法：按语言偏好取值（`LOCALE_PREFERENCE = zh-rCN → zh → default → zh-rSG → zh-rHK → zh-rTW → en`），
实现进产品模块 `mihome_pc/xiaomi/arsc.py`（`table_texts` / `package_texts` / `config_locale`），
工具 `tools/arsc_map.py` 变成它的命令行外壳，另有 `tools/plugin_texts.py` 做「名字 → 文案 + 代码引用统计」。

实测（`python tools/plugin_texts.py out/plugins/minij.washer.apk`）：

```
string resources: 360 (with Chinese: 339)
clean_mode_can_not_order -> '筒自洁模式下不能预约，请重新选择模式'
```

### 10.2 关键反证：这条规则文案**没有任何代码引用**

| 检查 | 结果 |
|---|---|
| 584 个 java 里有 `R.string.clean_mode_can_not_order` | **0 处**（只有 `R.java` 的定义） |
| 代码里出现它的数字 id `0x7f0b0026` / `2131427366` | 0 处 |
| `classes.dex` 里 `const-string "clean_mode_can_not_order"` | **0 个方法引用**（`tools/dex_literal_refs.py` 全量扫 class_data→code_item） |
| 资源 XML（407 个）里有 `@string/clean_mode_can_not_order` | 0 处（只有 strings.xml 的定义与 public.xml） |

对比：360 条 string 资源里 **212 条**被 `R.string.xxx` 引用（例如 `washer_setting`），**148 条**没有被任何
java 引用。而把这 148 条拿去 dex 里查**字面量**，**148/148 全在**——即插件把「资源名」当字符串留在了 dex 里，
给宿主（米家 App 的通用插件框架 / 布局 XML）按名字去解析，而不是自己 `R.string` 引用。

所以 §9.1 那句「这证明插件的业务规则是硬编码在代码里的」**站不住**：
资源里出现一句提示语，只能证明**有人可能需要显示它**，不能证明是插件代码在显示它。

### 10.3 对「拿下代码级规则」的影响

* 文案表这件事**已经彻底通了**：名字、简体中文、多语言分片、故障码解释（`通讯故障（CE）`、`门锁故障（dF）` 等）都能取；
  `plugin-sync` 现在同时写 `strings.json`（扁平）和 `texts.json`（具名），洗衣机 542/339、电视 77/59。
* 「规则在插件 Java 里、grep 就能拿到」这条**证伪**。要在本产品里落地可用性规则，现实的三条路是：
  1. **真机矩阵探测**（已有 `probe --commit` + 写后回读）：唯一能产出「什么状态下允许什么」的可靠证据；
  2. **宿主框架**（主 APK 的 RN bundle `assets/rn_plugins/miot.switch.spec.zip`）里的 enable/disable 判定——
     那是通用 UI 的禁用逻辑，但这是主 App 的代码，不是插件的；
  3. **云端返回的拒绝码**：`prop/set` 的负数 code 是设备/云端的最终裁决，可以按码建语义表。
* 插件文案的新用途（比规则更实用）：故障码 → 中文解释、程序名、状态话术，直接进 UI。
