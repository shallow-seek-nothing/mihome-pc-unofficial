## 2. nonce / sessionSecurity / signature

### nonce

```java
// _m_j/ys2.java:22-32
ByteArrayOutputStream out; DataOutputStream d;
d.writeLong(new SecureRandom().nextLong());            // 8 字节随机
d.writeInt((int) ((System.currentTimeMillis() + j) / 60000));   // ★ 固定 4 字节
return base64(out.toByteArray());                       // = jm0.OooOOoo
```
`j` = **服务端时间偏移**（`MiServiceTokenInfo.OooOoo0`），用于校正本机时钟。

> 与 v2 的差异：v2 把分钟数按"最小字节数"编码；APK 是**固定写 4 字节 int**。
> 2026 年的分钟数约 29,896,000（需 25 bit），所以两者碰巧等价，
> 但 v3 按 APK 写成固定 4 字节。

### sessionSecurity

```java
// _m_j/wrf.java:645-651
byte[] ssec  = base64decode(serviceToken.ssecurity);
byte[] nonce = base64decode(_nonce);
String sessionSecurity = base64( sha256(ssec ‖ nonce) );    // 32 字节
```
（`OooO0oO` = sha256，`nfa.OoooOOo` = base64 编码）

### signature

```java
// _m_j/ys2.java:34-65
List<String> parts;
parts.add(method.toUpperCase());
parts.add(Uri.parse(url).getEncodedPath());          // ★ 取 URL 编码后的 path
for (entry : new TreeMap(map).entrySet())            // ★ 按键字典序
    parts.add(key + "=" + value);
parts.add(sessionSecurity);
signature = base64( sha1( join("&", parts) ) );
```

### ★ 顺序的真相（吃掉一整晚的那个坑）

APK 的 body 是**按 TreeMap 顺序**逐个 append 的（`wrf.java:683-693`），
签名也迭代同一个 TreeMap —— 也就是说 **body 顺序 == 签名顺序**。

v2 用 Python dict 插入序，同样满足"顺序一致"，所以也能通过。
**真正的不变式是：签名时的键顺序必须与表单提交的键顺序完全一致**，
字典序只是 APK 的选法。

v3 直接照抄字典序，两边都对齐 APK。

## 3. 两种加密模式（11.9 新增 AES-GCM）

分派按 header `MIOT-ENCRYPT-ALGORITHM` 的值。

### 3.1 ENCRYPT-RC4（v2 用的，仍然可用）

```java
// _m_j/wrf.java:636-695  OooOO0o()
headers += ("MIOT-ENCRYPT-ALGORITHM", "ENCRYPT-RC4");
headers += ("Accept-Encoding", "identity");
nonce = generateNonce();
sessionSecurity = b64(sha256(b64d(ssecurity) ‖ b64d(nonce)));
TreeMap plain = params;
plain["rc4_hash__"] = sign(method, path, plain, sessionSecurity);
TreeMap enc;
for (k, v) in plain:                      // TreeMap → 字典序
    enc[k] = base64( rc4(sessionSecurity).crypt(v.getBytes(UTF_8)) );
body = enc ++ [ ("signature", sign(method, path, enc, sessionSecurity)),
                ("_nonce", nonce),
                ("ssecurity", ssecurity) ]        // ★ RC4 模式带 ssecurity
```

RC4 实现（**必须是同一个状态对象**）：

```java
// _m_j/g7c.java:19-28
g7c(byte[] key) {                 // key 必须 32 字节
    this.state = new ew0(key, 3);        // KSA
    this.crypt(new byte[1024]);          // ★ 先烧 1024 字节密钥流
}
// _m_j/ew0.java:39-53 —— 标准 RC4 PRGA，无私有变换
bArr[i] ^= S[(S[i+1] + S[j]) & 255];
```

`ew0` 就是教科书 RC4：KSA `j = (j + S[i] + key[i % keylen]) & 255; swap`，
PRGA 标准。**没有**魔改。

### 3.2 ENCRYPT-AES（新，AES-128-GCM）

```java
// _m_j/zd.java:115-148  OooOO0o()
headers += ("X-XIAOMI-PROTOCAL-FLAG", "PROTOCAL-HTTPS");
headers += ("X-XIAOMI-PROTOCAL-FLAG-CLI", "PROTOCAL-HTTP2");
headers += ("MIOT-ENCRYPT-ALGORITHM", "ENCRYPT-AES");
byte[12] iv = random();                       // ★ 12 字节 IV
for (k, v) in params:                          // TreeMap → 字典序
    enc[k] = base64( AES_GCM(key=sessionSecurity, iv=iv, tag=128, v) );
ivB64 = base64(iv);
aes_hash__ = ivB64;
body = enc ++ [ ("aes_hash__", ivB64),
                ("signature", sign(method, path, enc + aes_hash__, sessionSecurity)),
                ("_nonce", nonce) ];
                // ★ AES 模式不带 ssecurity 字段
```
响应：`base64decode → AES-GCM 解密 → (可选) gunzip → UTF-8`。

> 这条是 v2 完全没覆盖的能力。v3 两种都实现，默认 RC4（兼容性最好），
> AES 作为可切换实现（有些新接口可能只认它）。

### 3.3 响应解码（两种模式共用形状）

```java
// _m_j/wrf.java:618-634
plain = base64decode(respBody);
plain = rc4(sessionSecurity).crypt(plain);
if ("GZIP".equals(headers.get("MIOT-CONTENT-ENCODING")))
    plain = gunzip(plain);
return utf8(plain);
```
即 `base64(RC4(gzip(json)))` —— 与交接文档一致，**解完 RC4 还要 gunzip**。

注意：`g7c.OooO00o` 里 gunzip 不是看响应体前两字节，而是**看 header
`MIOT-CONTENT-ENCODING` 是否为 `GZIP`**。v2 靠 `\x1f\x8b` 嗅探，实测也够用，
但 v3 以 header 为准、嗅探作兜底。

## 7. 与 v2 实现的差异清单（v3 要改的点）

| 项 | v2 | 逆向结论 | 处理 |
|---|---|---|---|
| base URL | `api.io.mi.com` | CN 已改 `api.mijia.tech` | 换默认，保留回退 |
| 签名键序 | 插入序 | 字典序（TreeMap） | 改字典序 |
| 签名 path | 原样 | `Uri.getEncodedPath()` | 用 urllib 编码 |
| nonce 分钟 | 变长 | 固定 4 字节 int | 改固定 |
| nonce 时钟 | 无偏移 | 服务端时间偏移 `j` | 记录 serverTime delta |
| gunzip 判定 | 嗅探 `\x1f\x8b` | header `MIOT-CONTENT-ENCODING` | header 优先 |
| timezone cookie | `GMT+08:00` | URL 编码的显示名 | 按 APK |
| 缺的 cookie | — | `timezone_id`/`is_daylight`/`dst_offset` | 补上 |
| 加密模式 | 仅 RC4 | RC4 + AES-GCM | 两种都实现 |
| spec 来源 | 预置 14 份 | `spec_type` + 云批量端点 | 动态获取 + 本地缓存 |

真机返回（截断）：

```json
{"module_datas": [
  {"name": "fault", "count": 0, "type": "", "data": {"device_list": [
     {"did":"<did>", "model":"careli.fryer.maf04",
      "target_prop":"prop.2.2", "target_values":[], "exclude_values":["0"],
```

要点：

* **服务端已经算好** count / hidden / cur_value，客户端只做渲染。

* 判定规则（OooO0OO.java:530）：
  * working / existing / security → cur_value ∈ target_values
  * fault → cur_value ∉ exclude_values
* countdown_prop + countdown_value 给出「剩余 N 分钟」。
* 分类名常量见 StatusItemModule：fault / working / existing / security / env / consumable / speaker / speaker_exist / hmind。
* 显示名与排序权重来自 AppConfig 的 home_status_resource（OooO0OO.java:778），我们本地用中文常量表代替。

## 10. 场景执行 `NewRunScene`（2026-11-21 实测）

场景页要「点一下执行」，光有 `scene_id` 不够。真机试出来的请求体：

```
POST /appgateway/miot/appsceneservice/AppSceneService/NewRunScene
{
  "scene_id":   "<scene_id>",
  "scene_type": 2,                      // 必填，0 会 -8
  "phone_id":   "<设备 id / 任意非空>",   // 必填
  "home_id":    "<home_id>",             // 共享家庭时需要
  "owner_uid":  "<owner_uid>"           // 家庭所有者的 uid
}
→ true                                  // 注意：成功返回的是布尔 true，不是 {code:0}
```

踩到的三个坑：

1. **`scene_type` 是必填**：缺省/0 → `-8 invaild scene_type, scene_type=0`；
   用 1（`CommonUsedScene.OLD_TYPE`）→ `sceneInfo is empty`；
   用 2（`CommonUsedScene.SPEC_SCENE_TYPE`，`GetSimpleSceneList` 出来的场景就是这个类型）→ 成功。
   证据代码：`com/xiaomi/smarthome/scene/bean/CommonUsedScene.java:13-14`、
   `_m_j/grc.java:36-52`（请求体字段）、`scene/api/OooO0o.java:1301`（方法签名）。
2. **成功响应是 `true`**：按 `{code:...}` 解析会把成功误判成失败（我们的 provider 一开始就是这样）。
3. **`scene_id` 是字符串**：JSON 里当数字发，网关会报 `invalid character 'o' in literal null` 这类解析错。

场景列表本身的字段（`manual_scene_info_list[].scene_action.actions[].payload_json`）
见 `mihome_pc/domain/scene.py` 的注释；执行只认 `manual_scene_info_list` 里的 id，
`auto_scene_info_list` 是条件触发的自动化，不能手动执行。
