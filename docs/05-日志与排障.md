# 日志与排障

这份文档的目标只有一个：**用户贴一行字，开发就能定位**。所以日志格式是固定的，
失败弹框里带的是同一个请求 id，`mihome-pc report` 打出来的包可以直接附到 issue。

## 1. 日志在哪

| 平台 | 路径 |
|---|---|
| Windows（安装版 / 绿色版） | `%USERPROFILE%\.mihome-pc\logs\mihome-pc.log`；绿色版在程序目录的 `data\logs\` |
| Linux（deb / tarball） | `~/.mihome-pc/logs/mihome-pc.log` |
| 自定义 | 设 `MIHOME_PC_HOME`，日志就在 `$MIHOME_PC_HOME/logs/` |

目录里可能有这些东西：

```
logs/
├─ mihome-pc.log       当前日志
├─ mihome-pc.log.1 …   滚动档（默认 2 MiB 一个，留 5 份，约 12 MiB 封顶）
└─ crash-20261126-192301.log   未捕获异常的完整 traceback + 环境信息
```

启动时终端会打印 `log: <路径>`，`mihome-pc selftest --env` 也会列出日志路径、当前级别、崩溃记录数量。

## 2. 一行日志长什么样

```
2026-11-26T19:26:15.007+08:00 WARNING web      ec383171 api GET /api/device -> 400: did required
└─────────── 时间（ISO8601，毫秒 + 时区）    └─ 级别  └模块  └请求 id  └──────── 正文 ────────┘
```

- **时间**：`2026-11-26T19:26:15.007+08:00`，带毫秒和时区偏移。跨机器不用再对时，也别再报「几点几分」这种没法查的时间。
- **级别**：`DEBUG` / `INFO` / `WARNING` / `ERROR`。
- **模块**：`web`（HTTP 层）、`cloud`（米家云端）、`app`（桌面/托盘/停止）、`cli`、`auth`、`crash`。
- **请求 id**：8 位十六进制，一次 HTTP 请求一个；同一请求内所有日志、响应的 `X-Request-Id` 头、失败弹框里的「请求 ID」都是同一个值。没有请求上下文时是 `-`。

常见正文形态：

```
INFO  web      4b3226e3 GET /api/devices -> 200 in 15ms
WARNING web    ec383171 api GET /api/device -> 400: did required
INFO  cloud    4b3226e3 call /app/miotspec/prop/set http=200 code=0 in 126ms (312 bytes)
WARNING cloud  4b3226e3 call /app/miotspec/prop/set http=200 code=-704010000 after 118ms: invalid value
ERROR web      -        unhandled POST /api/set
Traceback (most recent call last):
...
```

云端每次调用都会记：接口路径、HTTP 状态、协议 `code`、耗时、响应字节数。**成功也记**——
排障时「到底调没调、多久、返回码是多少」同样关键，只记失败会让人怀疑请求根本没发出去。

## 3. 级别怎么调

```bash
mihome-pc --log-level debug serve      # 最详细（请求、云端调用、内部决策）
mihome-pc --log-level warning serve    # 只看异常
MIHOME_PC_LOG_LEVEL=debug mihome-pc serve   # 等价环境变量
```

默认 `info`。`debug` 会把静态资源请求也记下来，排障完记得调回去。

## 4. 密钥一定会被打码

写盘前统一脱敏，规则在 `mihome_pc/logs.py: redact_text()`：

| 原始 | 日志里 |
|---|---|
| `serviceToken=a1b2c3d4e5f60718293a4b5c6d7e8f90` | `serviceToken=a1b2…(32)` |
| `{"passToken": "0123456789abcdef..."}` | `{"passToken": "0123…(32)"}` |
| `Authorization: Bearer eyJhbGciOi...` | `Authorization: Bearer eyJh…(N)` |

- 保留前 4 位与长度：够判断「是哪一把、换没换」，又不可复用。
- **错误码、设备 did、接口路径不脱敏**——这些是排障必需信息（早期版本差点把 `code` 也打掉）。
- 诊断包（`mihome-pc report`）**不含** `credentials.json`，也不含设备 token 明文。

## 5. 失败弹框（界面）

界面上任何操作失败不再是一闪而过的 toast，而是一个诊断框：

- **标题**：哪个操作失败了（如「运行场景失败」）。
- **说明**：服务端返回的人话错误。
- **元信息**：请求 ID · HTTP 状态 · 协议 code · 接口路径。
- **复制诊断信息**：一键复制下面这些字段，贴到 issue 里即可：

```
操作：运行场景失败
时间：2026-11-26T19:26:15.448Z
错误：invalid value
接口：/api/scenes/run
状态：HTTP 200
错误码：-704010000
请求 ID：ec383171
版本：0.7.40
日志：数据目录 logs/mihome-pc.log（mihome-pc report 可打包）
```

带 `请求 ID` 的那一行，和日志里的 `req=ec383171` 是同一个值——用户在日志里
`grep ec383171` 就能看到这一次请求的全部上下文（包括它调了哪些云端接口）。

## 6. 报 bug 的标准动作

```bash
mihome-pc report            # 生成 <数据目录>/mihome-pc-report-<时间>.zip
```

压缩包里是：

- `environment.txt`：版本、Python 版本、系统、架构、数据目录、日志级别、有无凭据；
- `logs/*.log*`：当前日志 + 滚动档 + 崩溃档。

**不含**凭据文件与设备 token。让用户只发这一个 zip，比来回问「你什么系统、什么时候、点了什么」省时间。

## 7. 排障对照表

| 现象 | 先看什么 |
|---|---|
| 界面停在演示模式 | `selftest --env` 的「凭据」行；日志里 `provider -> demo/cloud` 那行 |
| 某个按钮失败 | 弹框里的请求 ID → `grep <请求 ID> logs/mihome-pc.log` |
| 云端一直失败 | 日志里 `call <路径> ... code=<code>`；`-704010000` 多是参数/能力不支持，`code 2/3/401` 是 token 失效（重新扫码） |
| 程序闪退 | `logs/crash-*.log`（pythonw 下没有控制台，这里是唯一现场） |
| 磁盘被日志吃满 | 滚动已限制在约 12 MiB；异常时手动删 `logs/mihome-pc.log.*` |
| 看不到任何日志 | 确认进程有写数据目录的权限；日志被禁用时 `selftest --env` 的「日志」行会显示路径但文件不存在 |

## 8. 约定（改代码时请遵守）

1. 新代码别 `print`，用 `logs.get("<模块>").info(...)`；`print` 只留给 CLI 的用户可见输出。
2. 一条日志里**不要自己拼时间**，格式化器统一加。
3. 参数用惰性格式化（`log.info("x=%s", value)`），不要先 `%` 成字符串再传。
4. 涉及密钥时可以直接写（脱敏在写盘前统一做），但**别把整份凭据 JSON 塞进日志**。
5. 失败分支至少一条 `WARNING`，未捕获异常走 `ERROR` + traceback（HTTP 层已自动做）。
